# Redaction Notice — Metadata Fields

**Date of notice:** 2026-05-10
**Files affected:**
- `daily_predictions/2026/05/2026-05-07.json`
- `daily_predictions/2026/05/2026-05-08.json`

## What happened

On 2026-05-10, during a routine audit of the public prediction stream, we identified that the `metadata` block of the two daily prediction files listed above contained operational fields that were never part of the intended public commitment:

- `bocpd_prob_changepoint` — an internal probability reading from the regime-detection layer
- `risk_layers_active.{bocpd, cbf_qp, rcpo}` — implementation labels of three internal risk-management layers
- `user_id` — a private per-account identifier used internally to route between paper and live execution contexts

These fields were generated by the publisher pipeline as diagnostic instrumentation and inadvertently included in the public payload. They are operational implementation detail, not part of the cryptographic commitment that constitutes the public track record.

## What the public commitment actually covers

The verifiable, append-only commitment of this repository is:

- `model_sha256` — proves the model has not changed since freeze
- `weights` — the portfolio allocation generated for the day
- `orders` — the orders submitted to the broker following those weights
- `portfolio.{total_value, cash, n_positions}` — the top-line portfolio state
- `publication_time_utc` — the timestamp at which the commit was created
- `content_sha256` — a self-hash of the payload that any third party can recompute and verify

Those fields are unchanged. The cryptographic integrity chain of the track record is intact and verifiable.

## Why we are not editing the historical files

The `content_sha256` of each daily prediction is a self-hash of the full payload as published. Editing the historical files to remove the metadata fields would change their hash and break the integrity chain that the project commits to maintain. Force-pushing to rewrite git history would similarly invalidate every commit SHA referenced by external auditors.

Both options would deliver superior privacy at the cost of breaking the cryptographic transparency promise. We consider that an unacceptable trade-off in a project whose entire value proposition is "auditable, append-only research log".

We therefore preserve the original files unmodified and disclose the issue here, in the public repository, as part of the audit trail.

## Action taken going forward

Publishes from `2026/05/2026-05-11.json` onward omit the affected fields entirely. Future `metadata` blocks contain only `model_version`, `orders`, `portfolio`, and `dry_run`.

The production inference image was rebuilt on 2026-05-10 (digest `sha256:81f894d3377c94dfeb7759051ed7774d486aef85b26baac7ac86c73936b905c2`) and is the image executing every daily cron from that date forward.

## How to verify

Any third party can confirm that the historical files remain unchanged:

```bash
# Compute the actual hash of the payload (without content_sha256 field):
jq 'del(.content_sha256)' daily_predictions/2026/05/2026-05-07.json \
  | jq -c -S . \
  | sha256sum
# Compare against the content_sha256 value declared in the file:
jq -r '.content_sha256' daily_predictions/2026/05/2026-05-07.json
```

Both should match. The same verification on files dated 2026-05-11 and later will pass with the cleaner metadata schema.
