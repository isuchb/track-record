# Redaction Notice — Metadata Fields and Weights Normalisation

**Date of notice:** 2026-05-10 (original) — amended 2026-05-15
**Files affected:** every daily prediction file from 2026-05-07 through 2026-05-14 inclusive.

This notice has two parts.

 Part 1 documents an inadvertent inclusion of operational metadata; Part 2 (added 2026-05-15) documents a separate issue with the numeric scale of the `weights` field. The cryptographic integrity chain of the repository is intact in both cases — no historical file is being modified, only disclosed.

---

## Part 1 — Operational metadata fields (notice date 2026-05-10)

**Files affected:**
- `daily_predictions/2026/05/2026-05-07.json`
- `daily_predictions/2026/05/2026-05-08.json`

### What happened (metadata fields)

On 2026-05-10, during a routine audit of the public prediction stream, we identified that the `metadata` block of the two daily prediction files listed above contained operational fields that were never part of the intended public commitment:

- `bocpd_prob_changepoint` — an internal probability reading from the regime-detection layer
- `risk_layers_active.{bocpd, cbf_qp, rcpo}` — implementation labels of three internal risk-management layers
- `user_id` — a private per-account identifier used internally to route between paper and live execution contexts

These fields were generated by the publisher pipeline as diagnostic instrumentation and inadvertently included in the public payload. They are operational implementation detail, not part of the cryptographic commitment that constitutes the public track record.

### Action taken (metadata fields)

Publishes from `2026/05/2026-05-11.json` onward omit the affected fields entirely. Future `metadata` blocks contain only `model_version`, `orders`, `portfolio`, and `dry_run`. The production inference image was rebuilt on 2026-05-10 (digest `sha256:81f894d3377c94dfeb7759051ed7774d486aef85b26baac7ac86c73936b905c2`).

## Part 2 — Weights normalisation (notice date 2026-05-15)

**Files affected:** all daily prediction files from `2026-05-07.json` through `2026-05-14.json` inclusive.

### What happened (weights normalisation)

On 2026-05-15 we identified that the `weights` field in the daily prediction JSON files dated between 2026-05-07 and 2026-05-14 contains the raw model action vector instead of the normalised target portfolio weights.

In Shield v1 the trading policy is a continuous-action neural network that emits a vector of per-asset scores. The downstream order-construction layer normalises this vector (dividing each component by the sum) before computing trade orders, so that the resulting target portfolio sums to one. The published JSON inadvertently captured the **pre-normalisation** vector rather than the normalised one. The raw vector for those eight publications sums to approximately 12.5, with each per-ticker value clustered around 0.5; the normalised target portfolio that was actually executed has the same per-ticker proportions divided by ~12.5, so each ticker's true target weight is approximately 4%.

### Confirmation that executions were correct

The order-construction code normalises internally, so the broker fills correspond to the **normalised** target portfolio, not the published numbers. Specifically:

- For each affected day, the broker fills aggregate to roughly equal-weight across the 25-ETF universe (about 4% per ticker).
- The order amounts published in the same JSON (`metadata.orders[*].delta_value`) are consistent with the normalised portfolio, not with the inflated raw weights.
- The portfolio's mark-to-market value (`metadata.portfolio.total_value`) is consistent with the executed normalised portfolio.

### Why we are not editing the historical files

As stated in Part 1, the `content_sha256` of each daily prediction is a self-hash of the file as published. Editing the historical files would break the integrity chain. We preserve them unmodified and disclose the issue here.

### Action taken (weights normalisation)

The publisher was patched on 2026-05-15 to normalise the action vector before signing. Publishes from `daily_predictions/2026/05/2026-05-15.json` onward emit weights that sum to approximately 1.0 and can be used directly to reconstruct the target portfolio.

The internal reconciliation Lambda was also patched on the same date: previously it compared the published weights against same-day fill deltas, which produced spurious "tracking-error" alerts because the two quantities are not on the same scale. The corrected Lambda compares the published target weights against the end-of-day portfolio composition (positions × prices ÷ portfolio_value), which is the correct reconstruction-vs-intent comparison.

### How to reconstruct the executed portfolio from a historical (pre-2026-05-15) file

For any affected file:

```python
import json
import urllib.request

url = "https://raw.githubusercontent.com/isuchb/track-record/main/daily_predictions/2026/05/2026-05-08.json"
data = json.loads(urllib.request.urlopen(url).read())

raw_weights = data["weights"]
total = sum(raw_weights.values())
normalised = {ticker: w / total for ticker, w in raw_weights.items()}
# `normalised` now sums to 1.0 and represents the actual target portfolio for that day.
```

This transformation is deterministic and reproduces the target portfolio that the order-construction layer used.

## What the public commitment covers

Across both notices the verifiable, append-only commitment of this repository remains:

- `model_sha256` — proves the model has not changed since freeze
- `weights` — the portfolio allocation generated for the day (normalisation per Part 2)
- `orders` — the orders submitted to the broker following the normalised weights
- `portfolio.{total_value, cash, n_positions}` — the top-line portfolio state
- `publication_time_utc` — the timestamp at which the commit was created
- `content_sha256` — a self-hash of the payload that any third party can recompute and verify

The cryptographic integrity chain remains intact and verifiable for every file in the repository.

## How to verify integrity (unchanged across both notices)

```bash
# Compute the actual hash of the payload (without content_sha256 field):
jq 'del(.content_sha256)' daily_predictions/2026/05/2026-05-07.json \
  | jq -c -S . \
  | sha256sum
# Compare against the content_sha256 value declared in the file:
jq -r '.content_sha256' daily_predictions/2026/05/2026-05-07.json
```

Both should match for every file dated 2026-05-07 onward.
